# DocFlow — сайт (MVP): лендинг, заявка на аудит, вход, кабинет

Пользователь отказался от уточняющих вопросов: все решения ниже приняты исполнителем, помечены как
«решение» там, где их можно оспорить.

## Зачем

Главная задача DocFlow — чтобы бизнес любой ниши мог спокойно и просто подключить распознавание документов.
Сайт закрывает путь клиента целиком:

1. **Знакомство.** Лендинг объясняет, что делает DocFlow и почему ему можно доверять. Ниша не важна:
   схема документа и справочники настраиваются.
2. **Заявка.** Форма аудита бизнеса и обсуждения внедрения: какие документы, сколько, куда их передавать.
3. **Вход.** Доступ в кабинет выдаётся после аудита (B2B, без самостоятельной регистрации).
4. **Работа.** Кабинет: загрузить документы, видеть очередь, проверять спорные документы в один клик,
   вести справочники, получить ключ API и подключить вебхук.

## Цели

- Публичный лендинг на русском с маркетинговыми блоками, без выдуманных цифр, отзывов и логотипов.
- Форма аудита с согласием на обработку персональных данных (152-ФЗ) и страница политики.
- Вход по email и паролю, сессия в httpOnly-cookie; кабинет закрыт для анонимов.
- Кабинет поверх существующего API: очередь, проверка, загрузка, справочники, интеграции.
- Запуск одной командой: сервис `web` в docker-compose.

## Не цели (MVP)

- Самостоятельная регистрация, восстановление пароля по почте, оплата и тарифы.
- Конструктор схем в интерфейсе (схемы пока через API/YAML).
- Мобильные экраны отдельным дизайном (сайт адаптивный, но отдельного мобильного макета нет — решение
  пользователя).
- Мультиязычность.

## Анти-цели (провал, даже если «работает»)

- Выдуманные показатели, отзывы, логотипы клиентов, цены. На лендинге — только то, что измерено
  (тест на 10 рукописных нарядах) или честно помечено «по итогам аудита».
- Обещание точности локального режима, которой нет: локальная модель — «черновик для оператора».
- Токен сессии или ключ API доступен JavaScript в браузере (localStorage, не-httpOnly cookie).
- Пароли в открытом виде или быстрым хешем; перебор пароля без ограничения.
- Заявка без согласия на обработку ПД; политика без реквизитов оператора (реквизиты — плейсхолдеры).
- Оператор подтвердил документ, а вебхук клиенту не ушёл.

## Архитектура

```
браузер ──► web (Next.js, :3000) ──server-side──► api (FastAPI, :8000) ──► Postgres / S3 / очередь
             cookie dfs_ (httpOnly)               Bearer dfs_… или dfk_…
```

- **web/** — Next.js 15 (App Router), TypeScript strict, Tailwind CSS v4. Все запросы к API делает сервер
  Next.js (Server Components, Server Actions, Route Handlers); браузер никогда не видит токен.
  Картинки страниц и PDF отдаются через Route Handlers, которые подставляют токен.
- **api** — существующий FastAPI. Добавляется: пользователи и сессии, заявки, список документов,
  статистика, превью страниц, ручная проверка, ключи API из кабинета, подсказки для справочников.

### Бэкенд: что добавить

| Что | Как |
|---|---|
| Пользователи | таблица `users`: tenant_id, email (уникален, в нижнем регистре), password_hash (argon2id, `argon2-cffi`), role `owner`/`operator`, disabled_at. CLI `docflow create-user <tenant_id> <email>` (пароль спрашивается или генерируется и печатается один раз). |
| Сессии | таблица `sessions`: sha256 токена `dfs_…`, user_id, expires_at (30 дней), revoked_at. `POST /v1/auth/login` → токен; `POST /v1/auth/logout`; `GET /v1/me`. Авторизация API принимает и `dfk_` (машины), и `dfs_` (люди). |
| Защита входа | одинаковый ответ на «нет такого email» и «неверный пароль»; лимит неудачных попыток: 5 за 15 минут на email и 20 на IP (в процессе API — решение: для MVP одного инстанса достаточно), затем 429. |
| Заявки | таблица `leads`; `POST /v1/leads` без авторизации: имя, компания, контакт, ниша, объём документов в месяц, какие документы, где хранят/куда передавать, сообщение, согласие (обязательно), honeypot-поле. Лимит 5 заявок в час на IP. Уведомление в Telegram, если заданы `DOCFLOW_LEADS_TG_TOKEN` и `DOCFLOW_LEADS_TG_CHAT` (ошибка отправки не роняет заявку). CLI `docflow leads` — последние заявки. |
| Список документов | `GET /v1/documents?status=&limit=&before=` — новые сверху, курсор по created_at. В элементе списка: id, статус, схема, номер/ключевые поля для показа (первые 3 строковых поля данных), первая проблема, created_at. |
| Статистика | `GET /v1/stats?days=30` — счётчики по статусам, доля ok без человека, сколько подтверждено вручную. |
| Превью страниц | конвейер сохраняет JPEG каждой страницы (то, что видит модель) в `pages/{id}/{n}.jpg`; `GET /v1/documents/{id}/pages/{n}`. |
| Ручная проверка | `POST /v1/documents/{id}/review` `{decision: "approve"\|"reject", data?, note?}`, только из `needs_review`. approve: данные прогоняются через normalize + справочники + evaluate заново (оператор увидит оставшиеся замечания), статус `ok` ставится решением человека; reject → `failed` с причиной. Пишется `reviewed_by`, `reviewed_at`, `review_note`; вебхук `document.completed` / `document.failed`. Повторная проверка — 409. |
| Ключи API из кабинета | `GET/POST /v1/api-keys`, `DELETE /v1/api-keys/{id}` — только для сессии владельца (`owner`); ключ показывается один раз. |
| Подсказки справочников | `GET /v1/dictionaries/{name}/suggestions` — значения из замечаний `not_in_dictionary` и `corrected` последних 200 документов с этим справочником, с частотой и ближайшим кандидатом. |

### Сайт: страницы

Публичные:

- `/` — лендинг (блоки ниже).
- `/audit` — форма аудита (та же форма есть в конце лендинга), после отправки — экран «заявка принята,
  ответим в течение рабочего дня» (срок — плейсхолдер `[СРОК ОТВЕТА]`).
- `/login` — вход; ссылка «нет доступа — оставьте заявку на аудит».
- `/privacy` — политика обработки ПД с плейсхолдерами реквизитов оператора.
- 404.

Кабинет (`/app/*`, только с сессией; middleware перенаправляет на `/login?next=`):

- `/app` — очередь: цифры (обработано, без участия человека, на проверке, ошибки), фильтр по статусу,
  таблица документов, «открыть следующий на проверку».
- `/app/documents/[id]` — проверка: превью страниц, поля по схеме (редактируемые; таблицы — строки),
  замечания с местом (поле), кнопки «подтвердить и отправить», «отклонить», скачать PDF.
  Для `ok`/`failed` — только просмотр.
- `/app/upload` — загрузка: выбор схемы, файлы (перетаскиванием), режим скана; после загрузки —
  ссылка на документ.
- `/app/dictionaries` и `/app/dictionaries/[name]` — список и редактирование (значения, написания,
  добавить/удалить, сохранить целиком через PUT), блок подсказок «модель прочитала не так».
- `/app/settings` — интеграции: ключи API (создать/отозвать, показать один раз), вебхуки
  (добавить/удалить, секрет один раз), короткая инструкция `curl`; аккаунт (email, клиент, режим модели,
  `auto_ok`), выход.

### Лендинг: блоки

1. Шапка: логотип, якоря (Как работает, Ниши, Безопасность, Интеграции, Вопросы), «Войти», «Аудит».
2. Первый экран: «Бумажные документы — сразу в вашу систему», подзаголовок про фото → PDF + данные +
   проверку; кнопки «Получить аудит» и «Как это работает».
3. Проблема: ручной перенабор — ошибки, время, сотрудник занят не тем (без выдуманных цифр).
4. Как работает: 4 шага — фото/скан → чистый PDF с текстом → данные по схеме → проверка и передача.
5. Что проверяем: ИНН/КПП/ОГРН/БИК/р/с, арифметика таблиц, даты, справочники; сомнение = на проверку.
6. Измерено: «10 рукописных заказ-нарядов: 100% полей верно, 7 из 10 — без человека, 3 — нашли реальные
   расхождения, включая ошибку в итоге, которую никто не заметил» (данные прогона 28.10.2026).
7. Ниши: зуботехнические лаборатории, бухгалтерия и аутсорс, логистика и склады, автосервисы, медицина,
   кадры — с примерами документов; «ваша ниша — настроим схему».
8. Безопасность и 152-ФЗ: локальный режим на сервере клиента, данные не уходят за периметр;
   честно — локальная модель даёт черновик, его проверяет оператор.
9. Интеграции: API, вебхуки с подписью, Excel/Telegram — в работе, 1С/Битрикс24/amoCRM — по плану
   (помечено «скоро»).
10. Как проходит внедрение: аудит → пилот на ваших документах с замером точности → подключение.
11. Вопросы (FAQ).
12. Форма аудита.
13. Подвал: контакты-плейсхолдеры, политика, вход.

## Дизайн: современный минимализм + брутализм (решение)

- Фон тёплый светлый `#F3F2EE`, текст `#0A0A0A`, один акцент — сигнальный красный `#E5231B`
  (на белом проверить контраст ≥ 4.5:1 для текста; для мелкого текста — тёмный вариант `#B8170F`).
- Шрифты: `Inter Tight` (заголовки, крупно, плотный трекинг, 400–600) и `JetBrains Mono` (метки, номера,
  цифры в таблицах) — оба с кириллицей, через `next/font`.
- Брутализм: видимая сетка и рамки 2px чёрные, нулевые скругления, жёсткие смещённые тени
  (`6px 6px 0 #0A0A0A`) у кнопок и карточек с «нажатием» на :active, нумерация секций `[01]`, метки капсом
  моноширинным. Минимализм: много воздуха, одна мысль на блок, никаких градиентов и иллюстраций-стоков.
- Кабинет — тот же язык, плотнее: таблицы с рамками, статус — квадратная метка, красный только для
  «на проверке/ошибка».
- Доступность: настоящие кнопки/ссылки/label, фокус-рамка видна, контраст 4.5:1, цели ≥ 44px,
  `prefers-reduced-motion`.

## Тестирование

- Бэкенд: pytest на каждый новый эндпоинт (включая изоляцию тенантов, лимиты входа, проверку из
  `needs_review` только один раз, вебхук после review), миграция 0003 в проверке миграций.
- Сайт: `tsc --noEmit`, ESLint, сборка `next build`; Playwright-смоук против поднятого стека:
  лендинг открывается, заявка уходит и видна через CLI, вход → очередь → открыть документ → подтвердить →
  статус ok; аноним на `/app` уходит на `/login`.

## Что оставлено исполнителю

Тексты блоков (без выдуманных фактов), точная вёрстка, иконки (инлайновые SVG), структура компонентов,
выбор библиотеки форм (без тяжёлых зависимостей).
