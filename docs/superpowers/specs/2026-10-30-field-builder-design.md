# DocFlow: конструктор полей и типов документов в кабинете

Пользователь, 30.10.2026: «Делай конструктор полей». Это продолжение страницы «Поля»
(`docs/superpowers/specs/2026-10-29-field-names-design.md`). Вопросов он не хочет, поэтому все решения ниже приняты
исполнителем.

## Зачем

Подписи полей компания уже меняет сама. Но добавить поле («Номер договора»), убрать лишнее, сменить тип или завести
свой тип документа («Путевой лист», «Товарная накладная ТОРГ-12») сейчас можно только через API, загрузив JSON-схему
версии. Клиент так не сделает. Без нас он не может подстроить продукт под свою нишу, а это главное обещание продукта.

## Цели

1. **Редактор типа документа в кабинете.**
   - Открывается со страницы «Поля» кнопкой «Изменить поля» у выбранного типа или кнопкой «Новый тип документа».
   - Адрес: `/app/fields/[slug]/edit` и `/app/fields/new`.
   - Шапка типа:
     - название;
     - описание — что это за документ, его видит модель;
     - для нового типа — служебное имя (slug), которое подставляется из названия транслитом и правится вручную.
   - Список полей верхнего уровня. Порядок меняется кнопками «выше» и «ниже» (без перетаскивания, это доступно с
     клавиатуры). У каждого поля:
     - название;
     - подсказка для модели (описание);
     - тип: Текст, Число, Целое число, Дата, Да/нет, Выбор из списка, Таблица;
     - «обязательное»;
     - проверка — одна из: нет, ИНН, КПП, БИК, ОГРН, СНИЛС, справочник (выбор из справочников тенанта), шаблон
       (regex);
     - «дата не в будущем».
   - Для «Выбор из списка» — варианты, по одному в строке.
   - Для «Таблица» — вложенный список колонок. Колонка — название, подсказка, тип (без таблицы и без проверок).
     Таблица в типе одна.
   - Служебное имя нового поля (`name`) строится из названия транслитом, латиница, цифры и `_`, уникально в
     схеме. После сохранения имя существующего поля не меняется: по нему хранятся данные и сопоставления.
     Показываем имя мелким серым, как на странице «Поля».
   - Особые поля «Номер документа» (`number`) и «Дата документа» (`issued`) предлагаются в новом типе по
     умолчанию. Решение исполнителя: удалить их можно, но редактор предупреждает, что без них документ в очереди
     и выгрузках будет без номера и даты.
   - «Удалить поле» спрашивает подтверждение. Если на поле ссылается правило документа (сумма таблицы, итог, счёт
     и БИК), редактор говорит, какое правило мешает, и не даёт удалить, пока правило не снято.
2. **Правила документа** (сверки между полями) показываются списком понятными фразами: «Сумма колонки «Сумма» =
   «Итого»», «Счёт сходится с БИК», «Итог = подытог + НДС». Их можно удалить. Добавить можно три самых частых:
   - сумма колонки таблицы = поле;
   - кол-во × цена = сумма в строке;
   - счёт сходится с БИК.
   Остальные правила сохраняются как есть, если пользователь их не трогал.
3. **Сохранение** делает новую версию через `POST /v1/schemas`, как сейчас:
   - старые документы остаются на своей версии;
   - новые документы идут по новой версии;
   - для встроенного типа появляется своё перекрытие тенанта.
   Ошибки сервера (422 от `DocSchema`) показываются у поля или правила, к которому относятся, иначе — общим
   сообщением. Перед сохранением — сводка изменений: «добавлено 2 поля, удалено 1, тип изменён у 1».
4. **Названия компании остаются при правке схемы.**
   - Подписи и выбор очереди хранятся по служебным именам и после новой версии продолжают действовать.
   - Подписи удалённых полей перестают мешать: `PUT /labels` больше не отвергает ключи, которых нет в последней
     версии, если они были в прошлых версиях. Решение исполнителя: при сохранении схемы подписи удалённых полей
     удаляются из набора, а ключи не из схемы по-прежнему 422.
   - В редакторе поле «название» правит `title` в схеме (для нового поля). Подпись компании, если есть, видна рядом
     и по-прежнему главнее.
5. **Откат к стандартному.** У встроенного типа, который тенант перекрыл, есть кнопка «Вернуть стандартные поля».
   Решение исполнителя: она сохраняет новую версию с телом встроенной схемы, а не удаляет историю, чтобы версии
   старых документов не потерялись.
6. **Новый тип сразу работает везде:** загрузка документов, правила маршрутизации, страница «Поля», реестр Excel,
   сопоставление в подключениях. Всё это уже читает список схем, исполнитель проверяет это.
7. **Формат API не меняется.** Редактор загружает схему через `GET /v1/schemas/{slug}?raw=true` (уже есть),
   без подписей компании. `DELETE` для схем не делаем.

## Не цели

- Удаление типа документа и переименование slug.
- Вложенные таблицы, несколько таблиц в типе, проверки у колонок.
- Произвольный конструктор правил документа: только три частых и удаление.
- Проверка нового типа на образце («прогнать фото») — отдельная работа.
- Совместное редактирование с блокировками: последний сохранивший создаёт новую версию. Решение исполнителя:
  перед сохранением сверяем, что последняя версия не изменилась с момента открытия редактора. Если изменилась —
  просим обновить страницу.

## Анти-цели

- Сохранение ломает уже обработанные документы, их выгрузки или PDF.
- Меняется служебное имя существующего поля, и данные или сопоставления теряются.
- Редактор отправляет схему, которую сервер отвергнет, без понятной причины для человека.
- Встроенная схема меняется для всех тенантов.
- Модель начинает получать подписи компании вместо описания схемы.

## Устройство (на усмотрение исполнителя в рамках этого)

- Бэкенд почти готов: `POST /v1/schemas`, `GET …?raw=true`, валидация `DocSchema`.
  - Добавить: при сохранении схемы чистить подписи и очередь от удалённых ключей.
  - Добавить: проверку «версия не изменилась» — `expected_version` в теле или query, 409 при расхождении.
  - Добавить: 422 с `loc`, указывающим поле или правило, если это возможно без переписывания валидации.
    Иначе — текст ошибки содержит имя поля в «ёлочках», и редактор находит поле по нему.
- Веб:
  - клиентский компонент редактора в `web/src/components/app/`;
  - чистые функции транслита и сборки или разбора схемы в `web/src/lib/`. Тестов для веба в проекте нет:
    исполнитель решает, стоит ли добавить минимальный тест-раннер для этих чистых функций (vitest) или проверить
    их на бэкенде. Решение исполнителя: логику, которую можно проверить на бэкенде (валидность итоговой схемы),
    проверяет `DocSchema`; транслит дублируется только в вебе.
- Живая проверка в браузере на демо:
  - добавить поле «Номер договора» в «Счёт»;
  - создать тип «Путевой лист» с таблицей;
  - загрузить документ этого типа (fake или демо-экстрактор) и увидеть поля в карточке.
