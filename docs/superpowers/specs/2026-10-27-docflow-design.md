# DocFlow — дизайн

## Зачем

Бизнесы каждый день вручную перепечатывают бумажные документы: счета, УПД, накладные,
паспорта, СТС, акты. DocFlow принимает фото или скан любого документа и возвращает:

1. **чистый PDF-скан с текстовым слоем** (замена ксерокса и сканера);
2. **структурированные данные** по схеме документа (JSON);
3. **решение о доверии к данным**: поля прошли проверки, или документ уходит человеку с указанием причин;
4. **доставку** в систему клиента: вебхук, API, позже коннекторы (1С, Битрикс24, amoCRM, Google Sheets).

Универсальность обеспечивают **схемы документов, а не код**. Новая ниша означает новые схемы,
а движок не меняется.

Основа взята из прототипа `helios-naryady`: подготовка фото (поиск листа, перспектива),
извлечение через Claude по строгой схеме, бизнес-проверки и прогон на эталонах. Принцип оттуда
сохраняется: **схема достаёт то, что написано; проверки решают, можно ли этому верить.**

## Цели

- API, через которое любой бизнес подключается за день: загрузить документ, получить результат
  или вебхук.
- Схемы документов задаются данными (JSON/YAML) и версионируются. В комплекте библиотека готовых
  схем для РФ.
- Два режима распознавания: облачный (Claude) и **локальный** (модель на своём GPU или сервере
  клиента) для персональных данных по 152-ФЗ.
- Проверки по предметной области: контрольные суммы ИНН, КПП, ОГРН, СНИЛС, БИК, р/с,
  арифметика таблиц, логика дат.
- Пофайловая оценка уверенности: сомнительные поля помечаются для человека.
- Измеримое качество: набор эталонов и метрики по полям на каждую схему.

## Не цели (на старте)

- Мобильное приложение в сторе (вход через веб, Telegram, API).
- Рукописный текст произвольной формы как основной сценарий (поддерживается моделью, но не
  оптимизируется).
- Собственное обучение OCR-моделей.

## Анти-цели (провал, даже если «работает»)

- Неверные данные молча уходят в систему клиента. Любое сомнение даёт статус `needs_review`,
  а не `ok`.
- Паспорт клиента, выбравшего локальный режим, уходит в зарубежное облако.
- Повторная отправка того же файла создаёт дубль в системе клиента (нужна идемпотентность).
- Внедрение требует программиста клиента дольше чем на день.

## Архитектура

```
Каналы ──► API (FastAPI) ──► очередь (Redis/arq) ──► воркер ──► хранилище результатов (Postgres)
веб, TG,     ключи, лимиты,                          конвейер:       │
почта, API   идемпотентность                         1 загрузка      ├─► файлы (S3/MinIO): оригиналы, PDF
                                                     2 подготовка    └─► вебхуки (HMAC, ретраи)
                                                     3 PDF + OCR
                                                     4 извлечение
                                                     5 проверки
```

| Слой | Решение |
|---|---|
| Язык, рантайм | Python 3.12, uv |
| API | FastAPI, Pydantic v2 |
| БД | PostgreSQL 16, SQLAlchemy 2 (async), Alembic |
| Очередь | Redis 7 + arq |
| Файлы | S3-совместимое (MinIO локально), интерфейс `BlobStore` |
| Изображения | OpenCV, Pillow, pillow-heif (фото с iPhone), pypdfium2 (PDF на входе) |
| PDF + текстовый слой | OCRmyPDF + Tesseract (`rus+eng`) в контейнере воркера |
| Извлечение (облако) | Claude Opus 5.5, structured outputs с JSON Schema, собранной из схемы документа |
| Извлечение (локально) | Ollama + Qwen2.5-VL 7B (влезает в 12 ГБ), JSON Schema в `format` |
| UI проверки (фаза 2) | Next.js + TypeScript + Tailwind + shadcn/ui |
| Бот (фаза 3) | aiogram 3 |
| Наблюдаемость (фаза 6) | OpenTelemetry, Prometheus/Grafana, Sentry |
| Поставка | Docker Compose; CI на GitHub Actions |

### Схема документа

Схема — это данные:

- `slug`, `version`, `title`, `description` (подсказка модели, что это за документ);
- поля: `name`, `type` (`string|integer|number|date|boolean|enum|table`), `description`,
  `required`, для `enum` — список значений, для `table` — колонки (те же типы, кроме `table`);
- проверки: на поле (`inn`, `kpp`, `ogrn`, `snils`, `bik`, `account`, `regex`, `date_not_future`)
  и на документ (`table_sum_equals`, `date_order`, `account_matches_bik`).

Из схемы генерируется JSON Schema для модели. Все поля обязательные, но nullable, плюс служебное
поле `_uncertain` со списком полей, которые модель видит, но не уверена в них. Этот приём
перенесён из Helios.

### Статусы результата

`ok`: обязательные поля есть, проверки пройдены, `_uncertain` пуст.
`needs_review`: всё остальное, с перечнем `issues` (поле, код, сообщение).
`failed`: обработка не удалась (ошибка модели, нечитаемый файл), с причиной.

## Фазы

| # | Фаза | Результат |
|---|---|---|
| 1 | **Ядро** | API + воркер + конвейер + схемы + проверки + вебхуки + эталонный прогон, всё в Docker Compose |
| 2 | UI проверки | Веб-кабинет: очередь `needs_review`, документ рядом с полями, правка одним кликом, правки сохраняются |
| 3 | Каналы | Telegram-бот, почтовый ящик (IMAP), загрузка с телефона через веб |
| 4 | Умные схемы | Схема из описания словами, автоопределение типа документа, разбиение пачки на документы |
| 5 | Коннекторы | Google Sheets, Битрикс24, amoCRM, 1С (OData/обмен файлами), нода n8n |
| 6 | Платформа | Мульти-тенант кабинет, тарифы и учёт страниц, наблюдаемость, лимиты |
| 7 | Пилот | Один реальный бизнес, замер «было/стало» |

Для каждой фазы пишется отдельный план. Этот документ — общий дизайн, план фазы 1 лежит рядом.

## Решения, принятые мной (можно оспорить)

- **arq, а не Celery**: конвейер асинхронный, у arq меньше настройки, и один Redis на всё.
- **Tesseract для текстового слоя, а не PaddleOCR**: OCRmyPDF даёт правильный PDF/A с
  выделяемым текстом из коробки. Точность слоя важна для поиска по документу, но не для
  извлечения полей, его делает VLM по картинке.
- **На старте тип документа указывает клиент** (`schema` в запросе); автоопределение вынесено
  в фазу 4.
- **Модель по умолчанию — Claude Opus 5.5**; локальный режим включается в настройках тенанта.
