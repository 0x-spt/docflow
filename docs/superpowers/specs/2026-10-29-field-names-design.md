# DocFlow: свои названия полей и сопоставление с системами клиента

Пользователь, 29.10.2026, после показа демо: «Имена полей и все куда вносятся данные, система сама должна
адаптироваться, дать удобную возможность компании самой отредактировать и выставить нужные ему имена полей».
Вопросов он не хочет, поэтому все решения ниже приняты исполнителем.

## Зачем

Сейчас компания видит наши названия полей: в очереди даже служебные имена (`bik`, `vat`, `buyer`). Поменять
подпись можно только одним способом: загрузить новую версию схемы через API. Сопоставление с системами
(какое поле в какую колонку или поле CRM) уже есть в форме подключения, но:
- коды полей CRM надо вписывать руками (`UF_CRM_…`, ID поля amoCRM), а узнавать их в самой CRM;
- своя Google Таблица клиента со своей шапкой получает строку в нашем порядке колонок, и данные ложатся мимо;
- переименуй поле — и наша же таблица, заведённая раньше, перестаёт принимать документы («другие колонки»).

Нужно, чтобы компания сама называла поля своими словами в одном месте кабинета, а всё остальное
подстраивалось само.

## Цели

1. **Свои названия полей (один слой поверх схемы).**
   - На каждый тип документа (slug схемы) у тенанта хранится набор подписей: ключ — имя поля верхнего
     уровня или `таблица.колонка`, значение — название компании.
   - Подписи действуют на **все версии** схемы, в том числе на старые документы: переименовал — везде
     поменялось.
   - Подписи видны везде, где поля видят люди:
     - кабинет: очередь, страница документа, форма проверки, правила, форма подключения;
     - цифровая версия PDF;
     - выгрузки: шапки Google Таблиц и Excel-реестра, уведомления (почта, Telegram), комментарии в CRM;
     - `GET /v1/schemas/{slug}`.
   - **Модель подписей не видит.** Извлечение идёт по исходной схеме, иначе переименование «НДС» в
     «Налог» ухудшило бы распознавание.
   - Проверка подписей:
     - после обрезки пробелов не пустая, не длиннее 80 символов, без управляющих символов;
     - среди полей верхнего уровня одной схемы подписи не повторяются (это колонки таблиц) — сравнение без
       учёта регистра;
     - ключ должен быть в последней версии схемы.
     Ошибка — 422 по-русски.
   - Пустое значение или отсутствие ключа — наше название по умолчанию.
2. **Что показывать в очереди.**
   - Компания выбирает до 3 полей верхнего уровня для колонки «Данные» очереди.
   - Без выбора действует умолчание вместо «первые поля по порядку». Берём наименование контрагента (первое
     строковое поле без правил реквизитов), итог (поле `total` из правил документа) и первую дату, кроме
     даты документа. Поля с правилами `inn`/`kpp`/`bik`/`ogrn`/`snils` и счёт из `account_matches_bik` по
     умолчанию не показываются.
   - Элемент `summary` в `GET /v1/documents` получает `label` (подпись с учётом названий компании);
     `field` остаётся для совместимости.
3. **Страница кабинета «Поля документов»** (`/app/fields`, пункт в навигации).
   - Слева или сверху — список типов документов тенанта (встроенные и свои).
   - Для выбранного — таблица строк:
     - поле: наше название и служебный ключ мелким серым;
     - «Ваше название» — поле ввода, пустое = по умолчанию;
     - «В очереди» — галочка, не больше 3.
     Колонки таблицы позиций идут отдельной группой.
   - Кнопка «Сохранить»; ошибки сервера — у поля.
   - Короткая подсказка: где применятся названия и что модель их не видит.
   - API: `GET /v1/schemas/{slug}/labels` — строки с ключом, типом, названием по умолчанию, текущей подписью и
     признаком «в очереди». `PUT /v1/schemas/{slug}/labels` с телом `{labels: {...}, queue_fields: [...]}`
     заменяет набор целиком.
4. **Google Таблицы подстраиваются.**
   - **Шапка наша** (A1 = «ID документа»). Отличаются только подписи, а число колонок и служебные колонки на
     своих местах — шапка переписывается новыми названиями, строка добавляется. Изменился состав колонок —
     ошибка как сейчас.
   - **Шапка клиента** (A1 другое). Строка раскладывается **по названиям колонок**. Значение попадает в
     колонку, если её заголовок после нормализации совпал с одним из вариантов:
     - название из сопоставления подключения;
     - название компании;
     - наше название по умолчанию;
     - служебное имя поля;
     - для служебных колонок — «ID документа», «Тип», «Номер», «Дата», «Статус», «Цифровая версия (PDF)»,
       «Кабинет».
     Нормализация: регистр, ё=е, пробелы, знаки препинания по краям.
     Колонки без пары остаются пустыми. Если не совпала ни одна колонка — ошибка «в таблице нет ни одной
     знакомой колонки» без повторов.
   - Лист позиций — так же.
5. **Поля системы подтягиваются из неё самой и подбираются автоматически.**
   - У коннектора появляется необязательный метод «поля системы». Он возвращает список
     `{code, title}`:
     - Google Таблицы — заголовки первой строки листа документов (code = заголовок);
     - Битрикс24 — пользовательские поля сделки `UF_CRM_*` из `crm.deal.fields`, название из
       `listLabel`/`formLabel`/`title`;
     - amoCRM — дополнительные поля сделок `GET /api/v4/leads/custom_fields` со всеми страницами (code = id);
     - 1С — фиксированные роли (`ROLES`), без сети.
     Почта, Telegram и вебхук полей не имеют.
   - API: `POST /v1/destinations/{id}/remote-fields?schema={slug}`. Отвечает
     `{fields: [{code, title}], suggested: {ключ поля документа: code}}`. Работает только для сохранённого
     получателя, с его секретами. Сбой системы — 502 с понятным текстом коннектора, секретов в ответе нет.
   - **Автоподбор.** Сначала точное совпадение нормализованного названия поля системы с названием компании,
     нашим названием или служебным именем. Затем словарь синонимов: ИНН, КПП, БИК, сумма/итого/к оплате,
     НДС, дата, номер, поставщик/продавец/контрагент. Затем похожесть (difflib, порог 0.8). Одно поле
     системы — одному полю документа. Для 1С подбор идёт по умолчаниям ролей.
   - **Форма подключения.** У сохранённого получателя с сопоставлением — кнопка «Подтянуть поля из
     <системы>». После неё:
     - вместо ввода кода — выбор из полей системы с названиями, ручной ввод остаётся возможен;
     - пустые строки заполняются предложениями, уже заполненные не трогаются;
     - видно, сколько полей подобрано.
     Без кнопки форма работает как сейчас.
6. **Мелочи из показа демо.**
   - Замечание в очереди показывается только у `needs_review` и `failed`: у одобренного документа не висит
     «нужно согласование».
   - Во встроенной схеме УПД исправить подпись `vat` («Всего к оплате» → «НДС») и описание поля
     «Расчётный счёт». Исполнитель проверяет, как `seed-schemas` обновляет встроенные схемы в БД, и
     решает: правка на месте или новая версия.

## Не цели

- Добавление, удаление и смена типа полей из кабинета: это конструктор схем, отдельная большая работа.
- Перевод подписей на другие языки.
- Создание полей в CRM за клиента.
- Перестройка готовой нашей таблицы при смене состава колонок.

## Анти-цели

- Переименование меняет то, что видит модель, или данные документов (`data` хранится по служебным именам).
- Подписи одного тенанта видны другому.
- Автоподбор молча перезаписывает сопоставление, которое клиент выставил руками.
- Запрос полей системы светит секреты в ответе, логе или тексте ошибки.
- Своя таблица клиента получает строку со сдвигом колонок.
- Старые подключения без сопоставления и наши таблицы без переименований начинают вести себя иначе.

## Устройство (на усмотрение исполнителя в рамках этого)

- Таблица `field_labels` (tenant_id, schema_slug, labels JSONB, queue_fields JSONB, updated_at), уникальна
  по (tenant_id, schema_slug); миграция Alembic.
- Чистая функция `apply_labels(schema, labels) -> DocSchema` (копия с заменёнными `title`). Применяется там,
  где схему видят люди:
  - `GET /v1/schemas/{slug}`;
  - `build_export_doc`;
  - цифровой PDF;
  - список документов.
  В конвейере извлечения не применяется.
- Чистые функции нормализации и автоподбора в отдельном модуле с юнит-тестами. Коннекторы тестируются
  на `httpx.MockTransport`, как остальные.
- Веб: Next.js 15, существующие компоненты кабинета (`Field`, `Button`), серверные actions как в
  `dictionaries`/`rules`.
- Живая проверка в браузере на демо-тенанте:
  - переименовать поле, увидеть его в очереди, документе и PDF;
  - выгрузка в Mailpit показывает новое название.
