# DocFlow — коннекторы: автовыгрузка и распределение по системам клиента

Пользователь (28.10.2026): «Давай сначала коннекторы» — сделать в продукте то, что обещает сайт: выгрузка
в 1С, Битрикс24, amoCRM, Google Таблицы, Excel, распределение по правилам, уведомления. Вопросы не задаются —
решения ниже приняты исполнителем и помечены.

## Что обещает сайт (источник требований)

- 1С (типовые конфигурации): документы поступления и реализации, контрагенты, номенклатура.
- Битрикс24 и amoCRM: сделки, контакты/компании, поля карточки; документ — в нужную сделку.
- Google Таблицы: строка на каждый документ, позиции — отдельным листом; таблица пополняется сама.
- Excel: реестр документов за период — шапка и позиции.
- Своя система: API и вебхуки (уже есть).
- Правила: тип документа → система; контрагент → ответственный/сделка его менеджера; сумма выше порога →
  согласование; проверка не сошлась → оператору.
- Уведомления: почта и Telegram — оператору о документе на проверку, ответственному о новом документе.

## Анти-цели

- Документ со статусом `needs_review` или `failed` ушёл в учётную систему клиента без подтверждения человеком.
- Один документ создал два поступления в 1С или две сделки в CRM (повторы, ретраи, повторная проверка).
- Секреты клиента (ключи, токены, пароли) лежат в БД открытым текстом или возвращаются из API.
- Ошибка выгрузки молча теряется: клиент должен видеть её в кабинете и иметь «Повторить».
- Коннектор шлёт запросы на частные адреса (SSRF), кроме явно разрешённых в dev.

## Архитектура

**Получатель (Destination)** — подключение тенанта к системе: `kind` (`google_sheets`, `bitrix24`, `amocrm`,
`onec_odata`, `telegram`, `email`), `name`, `config` (несекретное, JSON), `secrets` (зашифровано, Fernet,
ключ `DOCFLOW_SECRETS_KEY`), `mapping` (поле документа → поле системы, по схеме), `active`.

**Правило маршрутизации (RoutingRule)** — упорядоченный список правил тенанта: условия (схема документа;
сравнения полей: `=`, `≠`, `>`, `≥`, `<`, `≤`, «содержит», «есть в справочнике X», «пусто/не пусто»; все
условия через И) → действия: выгрузить в получателей [ids]; требовать согласования (документ остаётся/становится
`needs_review` с замечанием `approval_required` «нужно согласование: <название правила>»); уведомить получателей
уведомлений [ids]. Срабатывают все подходящие правила (не только первое), действия объединяются. Без правил
по умолчанию — ничего не выгружается (решение: клиент явно включает выгрузку).

**Когда срабатывает:** документ стал финальным для учёта — `ok` после конвейера (и тенант с `auto_ok`), либо
одобрен оператором (`document.reviewed`). Уведомление «на проверку» — при переходе в `needs_review`.
Согласование: правило с «требовать согласования» переводит `ok` → `needs_review` до выгрузки; одобрение
оператором снимает его (выгрузка идёт по остальным действиям).

**Выгрузка (Export)** — запись на пару (документ, получатель): статус `pending/done/failed`, попытки, последняя
ошибка, `external_id` (ID созданной сущности в системе клиента), время. Уникальность (документ, получатель) —
повторная выгрузка не создаёт дубль; ручное «Повторить» переотправляет только `failed`. Ретраи с бэкоффом как у
вебхуков (10 с, 1 мин, 5 мин, 30 мин, 2 ч), очередь arq, подбор зависших — как `requeue_stale`.

**Идемпотентность во внешних системах:** перед созданием ищем существующее по нашему ключу
(`docflow:<document_id>`): Google — строка уже содержит id документа в первой колонке; Битрикс24/amoCRM —
поле-метка/примечание с id и поиск; 1С — `Комментарий` содержит id, поиск по нему перед созданием.

## Коннекторы

| Коннектор | Подключение (секреты) | Что делает |
|---|---|---|
| Google Таблицы | сервисный аккаунт Google (JSON-ключ), ID таблицы; клиент даёт доступ email'у аккаунта | лист «Документы»: строка на документ (id, тип, номер, дата, поля по mapping, статус, ссылка на цифровой PDF); лист «Позиции»: строки таблиц документа с id документа. Заголовки создаются при первой выгрузке. |
| Битрикс24 | входящий вебхук портала (URL с ключом) | ищет компанию по ИНН (реквизиты) или названию, создаёт при отсутствии; создаёт сделку (название «<Тип> № <номер> от <даты>», сумма, поля по mapping, ответственный по правилу), прикладывает цифровой PDF и скан комментарием в таймлайне. |
| amoCRM | поддомен + долгосрочный токен интеграции | `leads/complex`: сделка + компания (поиск по ИНН/названию), поля по mapping, примечание со ссылками на PDF, тег `DocFlow`. |
| 1С (OData) | базовый URL публикации, логин, пароль | стандартный интерфейс OData (`/odata/standard.odata/`): контрагент по ИНН (`Catalog_Контрагенты`, создать при отсутствии), документ `Document_ПоступлениеТоваровУслуг` (входящие счета/УПД/накладные) или `Document_РеализацияТоваровУслуг` (по настройке правила) с табличной частью; номенклатура — поиск по наименованию, без создания (не найдена → выгрузка `failed` с понятной ошибкой). Имена объектов — по «Бухгалтерии предприятия 3.0», настраиваются в `config`. |
| Excel | — | `GET /v1/exports/excel?schema=&from=&to=&status=` → xlsx: лист «Документы» (шапка) и «Позиции»; кнопка в кабинете. |
| Telegram | токен бота, chat_id | сообщения: «на проверку: <документ>, причина», «новый документ: …» со ссылкой в кабинет. |
| Почта | SMTP host/port/логин/пароль/отправитель, получатели | те же уведомления письмом. |

Маппинг по умолчанию для встроенных схем (счёт, УПД) задаётся в коде; для своих схем клиент выбирает
соответствие полей в кабинете (селекты: поле документа → поле системы).

## API

- `GET/POST /v1/destinations`, `GET/PATCH/DELETE /v1/destinations/{id}` (владелец или ключ API; секреты
  принимаются, но никогда не возвращаются — только `has_secrets: true` и маска), `POST /v1/destinations/{id}/test`
  (проверка подключения без записи данных: Google — чтение метаданных таблицы; Битрикс24 — `profile`;
  amoCRM — `account`; 1С — `$metadata`; Telegram — `getMe`; почта — SMTP login).
- `GET/PUT /v1/routing-rules` (весь список упорядоченно, PUT заменяет целиком), валидация ссылок на получателей
  и поля схемы.
- `GET /v1/exports?document_id=&status=` — журнал выгрузок; `POST /v1/exports/{id}/retry`.
- `GET /v1/exports/excel?...` — реестр.
- В `document_payload`: `exports: [{destination, kind, status, external_id, error}]`.

## Кабинет

- «Интеграции» → подключения: список, добавить (форма по типу с подсказками, где взять ключ), «Проверить
  подключение», отключить/удалить, маппинг полей.
- «Правила»: список правил «если → то» с редактором условий и действий, порядок.
- Документ: блок «Выгрузки» — куда ушёл, ID во внешней системе, ошибка, «Повторить».
- Очередь: кнопка «Реестр в Excel» с периодом.

## Проверка

Все внешние API — через httpx (без SDK) и тестируются подменой ответов (respx) по документированным контрактам.
Живых аккаунтов Google/Битрикс24/amoCRM/1С сейчас нет: для живой проверки пользователь создаёт тестовые
(Битрикс24 и amoCRM — бесплатные пробные порталы, Google — сервисный аккаунт, 1С — учебная база с публикацией
OData); в README — пошаговая инструкция «где взять ключи». Это ограничение — в отчёт пользователю.
