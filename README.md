# DocFlow

Сервис, который превращает фото и сканы бухгалтерских документов в данные для учёта.

## Зачем

В небольшой компании счета, УПД и акты до сих пор приходят как придётся: фото в мессенджере, скан на почту, бумага,
которую кто-то сфотографировал на телефон. Дальше бухгалтер или менеджер сидит и перебивает это руками в 1С или CRM.
Это долго, скучно, и ошибки появляются именно тут: перепутанная цифра в ИНН, не тот расчётный счёт, итог, который не
сходится с суммой строк. Находят их потом, при сверке или когда платёж ушёл не туда.

DocFlow берёт эту работу на себя. Сотрудник просто пересылает документ боту в Telegram, отправляет на почту или
загружает в кабинет, а дальше:

- из фото получается ровный PDF с текстовым слоем и отдельно чистая цифровая версия документа;
- поля вытаскиваются по схеме документа: номер, дата, контрагент, реквизиты, таблица товаров, суммы;
- реквизиты проверяются: контрольные числа ИНН, КПП, БИК и расчётного счёта, совпадение счёта с банком, сумма
  таблицы с итогом, контрагент по справочнику компании;
- документ, к которому нет вопросов, сразу уходит дальше. Сомнительный попадает в очередь на проверку человеку, и
  там видно, что именно не так;
- проверенные данные выгружаются в 1С, Битрикс24, amoCRM, Google Таблицы, Excel или на вебхук.

Тип документа можно не указывать, сервис определит его сам. Набор полей компания настраивает под себя в кабинете,
без программиста: добавить «Номер договора» в счёт или завести свой «Путевой лист». Если документы нельзя отдавать в
облако (152-ФЗ), распознавание можно перевести на локальную модель.

Цель простая: человек смотрит только на те документы, где действительно есть проблема, а не перепечатывает все подряд.

## Как устроено

FastAPI, Postgres, Redis-очередь (arq) с отдельным воркером, S3-хранилище, кабинет на Next.js. Распознаёт Claude или
локальная модель через Ollama, OCR для текстового слоя делает Tesseract. Каналы приёма (бот и почта) работают
отдельным процессом. Всё поднимается одним `docker compose`.

API принимает фото или PDF и асинхронно возвращает PDF-скан с текстовым слоем,
данные, извлечённые по схеме документа (счёт, УПД, паспорт или своя схема), результат проверок реквизитов
(контрольные суммы ИНН/БИК/р/с, суммы по таблице) и вебхук. Статус `ok` — данным можно верить, `needs_review` —
нужна проверка человеком, `failed` — обработать не удалось. Внешние зависимости (модель, OCR, хранилище) скрыты
за протоколами, поэтому юнит-тесты идут без сети и Docker.

## Быстрый старт

```
export ANTHROPIC_API_KEY=sk-...   # передаётся в контейнеры; без ключа документы клиентов claude уйдут в failed
docker compose up -d --build      # postgres, redis, s3, migrate (миграции + схемы), api, worker
docker compose exec api docflow create-tenant "Ромашка"
# → API-ключ: dfk_...  (показывается один раз)
```

Загрузка, опрос, скачивание PDF:

```
KEY=dfk_...
curl -s -X POST http://localhost:8000/v1/documents \
  -H "Authorization: Bearer $KEY" -H "Idempotency-Key: $(uuidgen)" \
  -F schema=invoice_ru -F files=@schet.jpg            # несколько страниц — несколько -F files=@...
# → {"id": "…", "status": "queued"}

curl -s http://localhost:8000/v1/documents/<id> -H "Authorization: Bearer $KEY"
# → status: queued → processing → ok | needs_review | failed; data, issues, pdf_url, digital_pdf_url

curl -s -o scan.pdf http://localhost:8000/v1/documents/<id>/pdf -H "Authorization: Bearer $KEY"
curl -s -o digital.pdf http://localhost:8000/v1/documents/<id>/digital.pdf -H "Authorization: Bearer $KEY"
```

`GET /v1/documents/{id}/digital.pdf` отдаёт цифровую версию: PDF, набранный заново по извлечённым данным (не скан).
Заголовок берётся из поля `title` схемы (у полей и колонок `title` — подпись; без него печатается `name`). Доступна
в статусах `ok` и `needs_review` (иначе 409; чужой документ — 404; слишком длинные значения, которые не помещаются
на страницу, — 422). Ссылка `digital_pdf_url` приходит в ответе `GET /v1/documents/{id}` и в payload вебхуков
(как `pdf_url`; `null`, пока документ не готов). Шрифт с кириллицей задаётся `DOCFLOW_PDF_FONT_PATH`
(по умолчанию `/usr/share/fonts/truetype/dejavu/DejaVuSans.ttf`, в образе уже есть; жирное начертание ищется рядом:
`<имя>-Bold.ttf`). `docflow seed-schemas` при каждом запуске (его делает сервис `migrate`) обновляет и тела уже
засеянных встроенных схем, поэтому новые `title` доходят до существующих баз.

Повтор `POST` с тем же `Idempotency-Key` вернёт уже принятый документ. Документация API — http://localhost:8000/docs.

## Справочники

Клиники, врачи, контрагенты, склады — всё, что у клиента из фиксированного списка. Поле схемы с правилом
`{kind: dictionary, params: {name: clinics}}` сверяется со справочником `clinics` этого клиента:

- совпадение без учёта регистра, пробелов, пунктуации и ё/е → значение приводится к записи справочника;
- одна-две буквы не те («Дента-Локс») и кандидат единственный → исправляется, в `issues` — `corrected`
  (на статус не влияет);
- нет в справочнике или кандидатов несколько → `not_in_dictionary`, документ уходит на проверку. Выдуманное
  моделью название хуже пустого поля. `fuzzy: false` в правиле отключает автоисправление.

```
curl -s -X PUT http://localhost:8000/v1/dictionaries/clinics -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"title": "Клиники", "entries": [{"value": "Дента-Люкс"}, {"value": "Улыбка+", "aliases": ["Улыбка плюс"]}]}'
```

`PUT` заменяет справочник целиком (до 5000 записей), `GET /v1/dictionaries[/{name}]`, `DELETE /v1/dictionaries/{name}`.

## Доверие к модели (`auto_ok`)

Проверки ловят арифметику, контрольные суммы и даты, но не неверно прочитанную фамилию: сильная модель сама отмечает
сомнения (`_uncertain`), слабая ошибается уверенно. Поэтому у клиента есть флаг `auto_ok`: без него статус `ok` не
ставится, всё уходит в `needs_review` как черновик (`review_required`). По умолчанию — да для `claude`, нет для
`ollama`. Включать после эталонного прогона на документах клиента:

```
docker compose exec api docflow create-tenant "Лаборатория" --extractor ollama   # печатает id, auto_ok: нет
docker compose exec api docflow set-auto-ok <id> yes
```

## Сайт и кабинет

Сайт (`web/`, Next.js) — лендинг с формой заявки на аудит и кабинет клиента (очередь, проверка документов,
загрузка, справочники, ключи и вебхуки). Браузер токена API не видит: сессия — httpOnly-cookie `df_session`,
запросы к API идут с сервера сайта.

Запуск вместе со всем стеком:

```
docker compose up -d --build        # сайт: http://localhost:3000, API: http://localhost:8000 (только 127.0.0.1)
```

Клиент и его пользователь (пароль не короче 10 символов; без `--password` будет сгенерирован и показан один раз):

```
docker compose exec api docflow create-tenant "Моя компания"        # → id и API-ключ
docker compose exec api docflow create-user <tenant_id> boss@example.com --role owner --password '<пароль>'
```

Роли: `owner` (всё, включая ключи и вебхуки) и `operator` (очередь, проверка, загрузка). Вход — на `/login`.

Заявки на аудит из формы на лендинге сохраняются в БД: `docker compose exec api docflow leads`. Мгновенное
уведомление в Telegram включается переменными `DOCFLOW_LEADS_TG_TOKEN` (токен бота) и `DOCFLOW_LEADS_TG_CHAT`
(id чата); без них заявки просто лежат в БД. В заявке `POST /v1/leads` поле `targets` — список систем, куда
выгружать данные: `1c`, `bitrix24`, `amocrm`, `google_sheets`, `excel`, `own_system`, `unknown` (без повторов,
до 7; `null` или отсутствие поля — пустой список).

В проде:

- сайт и API за обратным прокси с TLS; в `docker-compose.yml` порты 3000 и 8000 опубликованы только на
  `127.0.0.1`, наружу смотрит лишь прокси;
- cookie получает флаг `Secure` в production-сборке, если не задано `COOKIE_SECURE=false`. В compose по умолчанию
  `false` (dev по http) — в проде за https задайте в `.env` `COOKIE_SECURE=true`;
- прокси обязан сам выставлять `X-Real-IP` адресом соединения и не пропускать присланный клиентом: в nginx
  `proxy_set_header X-Real-IP $remote_addr;` (и `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`).
  Сайт берёт адрес посетителя из `X-Real-IP`, без него — из последнего адреса `X-Forwarded-For`; первому адресу не
  верит. Этот адрес он передаёт API для лимитов на заявки и вход, а API верит ему только с общим секретом
  `DOCFLOW_INTERNAL_TOKEN` — одинаковым у сайта и API. Значения по умолчанию нет: задайте случайное в `.env`
  (пусто — API не верит адресу от сайта, и все посетители делят один лимит по адресу контейнера сайта);
- загрузка документов идёт через сайт, поэтому лимит тела ~200 MB (`client_max_body_size 200m;`) ставьте только
  на `location /app/upload`, на остальных адресах оставьте малый;
- `DOCFLOW_API_URL` у сайта — внутренний адрес API, наружу порт 8000 в проде не публикуется.

Сквозные тесты сайта (Playwright, против стека с fake-экстрактором; подробности — `web/README.md`):

```
docker compose -f docker-compose.yml -f docker-compose.e2e.yml up -d --build
cd web && npm ci && npx playwright install chromium && npm run test:e2e
docker compose up -d        # вернуть обычный воркер
```

## Подключения к системам клиента

Документы можно выгружать в Google Таблицы, Битрикс24, amoCRM, 1С (OData) и Excel-реестр, а операторов уведомлять
в Telegram и по почте. Подключение (кабинет → Подключения) хранит адрес и секреты, правила (кабинет → Правила)
решают, что куда уходит: без правил ничего не выгружается. Выгрузка идёт для готовых (`ok`) документов, в том числе
подтверждённых оператором; при сбоях доставка повторяется (10 с, 1 мин, 5 мин, 30 мин, 2 ч), результат виден в блоке
«Выгрузки» документа.

Секреты подключений шифруются ключом `DOCFLOW_SECRETS_KEY` (Fernet); сгенерировать и положить в `.env`, не коммитить:

```
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Смена ключа требует заново ввести секреты подключений. Пошагово, где взять ключи и токены каждой системы, примеры
правил и разбор типовых ошибок — в [docs/connectors.md](docs/connectors.md).

## Вебхуки

```
curl -s -X POST http://localhost:8000/v1/webhooks -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/hook", "events": ["document.completed", "document.failed", "document.reviewed"]}'
# → {..., "secret": "..."}  — секрет показывается один раз
```

События: `document.completed` — обработка закончилась (`ok` или `needs_review`), `document.failed` — не удалась
или отклонена оператором, `document.reviewed` — документ подтверждён человеком после проверки в кабинете (приходит
и подписчикам `document.completed`).

Тело — JSON `{"event": ..., "document": {...}}`, подпись — HMAC-SHA256 от сырых байтов тела в заголовке
`X-DocFlow-Signature: sha256=<hex>`. Проверка на Python:

```python
import hashlib
import hmac

def verify(secret: str, body: bytes, signature: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)

# Flask: verify(SECRET, request.get_data(), request.headers["X-DocFlow-Signature"])
```

Проверяйте подпись по полученным байтам, а не по заново сериализованному JSON. Неуспешные доставки повторяются
через 10 с, 1 мин, 5 мин, 30 мин, 2 ч. Вебхуки на частные адреса запрещены (`DOCFLOW_WEBHOOK_ALLOW_PRIVATE=true`
— только для dev, e2e и демо-оверлея `docker-compose.demo.yml`).

## Демо для показа клиенту

Готовый клиент «Демо» с 24 документами разных типов и статусов, цифровыми PDF и подключениями. Письма уходят в Mailpit.

```
docker compose -f docker-compose.yml -f docker-compose.demo.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.demo.yml run --rm worker docflow seed-demo
```

Команда печатает логин и пароль владельца и оператора и API-ключ — пароль и ключ показываются один раз. Кабинет:
http://localhost:3000/login, письма (Mailpit): http://localhost:8025. Письма приходят, когда воркер доставит
документы, обычно в пределах минуты. Повторный запуск: `seed-demo --reset` удаляет прежнего демо-клиента и создаёт заново.

Каждый `--reset` выдаёт новые пароли и API-ключ, а письма прошлых запусков остаются в Mailpit. Перед показом
очистите ящик, чтобы клиент не увидел старые письма:

```
curl -X DELETE http://localhost:8025/api/v1/messages
```

Внешние системы подключаются флагами `--google-key` и `--google-sheet`, `--bitrix-webhook`,
`--telegram-token` и `--telegram-chat`; без них — только почта. Подробности — в [docs/connectors.md](docs/connectors.md).

Оверлей разрешает вебхуки и подключения на частные адреса (`DOCFLOW_WEBHOOK_ALLOW_PRIVATE=true`) для всех
клиентов этого стека, не только для демо, и поднимает Mailpit без авторизации — в проде не использовать.

## Каналы приёма

Кроме загрузки в кабинете и API, документы приходят из Telegram-бота и почтового ящика клиента. Оба канала обслуживает
отдельный процесс `docflow channels` (сервис `channels` в compose): он опрашивает ботов и ящики, принимает файлы и
ставит документы в очередь; распознаёт их по-прежнему воркер. Токен бота и пароль ящика хранятся зашифрованными
(`DOCFLOW_SECRETS_KEY`, без него подключить канал нельзя).

**Telegram-бот.** Владелец кабинета на странице «Telegram-бот» вставляет токен от @BotFather. Бот работает через
long polling, публичный адрес не нужен. Отвечает он только привязанным чатам: сотрудник открывает ссылку-приглашение
`https://t.me/<бот>?start=<код>` из кабинета, и чат привязывается (кнопка «Новая ссылка» меняет код, старые привязки
остаются). Дальше в чат присылают фото или PDF: подпись, совпавшая с названием типа, задаёт тип, иначе берётся тип по
умолчанию из настроек бота; альбом из нескольких фото — один документ. Результат бот отвечает в тот же чат.

В группе бот должен видеть сообщения: сделайте его администратором группы или отключите режим приватности
(@BotFather → `/setprivacy` → Disable), иначе фото без обращения к боту до него не дойдут. Смена режима приватности
подействует, когда бота добавят в группу заново. Группу привязывают той же ссылкой (`?startgroup=<код>`).

**Почта.** Владелец на странице «Почта» указывает IMAP-сервер (порт 993, SSL), логин, пароль приложения и папку.
Процесс раз в минуту забирает непрочитанные письма: каждое вложение-PDF становится отдельным документом, картинки
одного письма — одним. Тема письма, совпавшая с названием типа, задаёт тип. **Разрешённые отправители** — адреса или
домены (`@firma.ru`); пустой список значит «принимать от всех», и тогда спам тратит страницы тарифа. Письмо от чужого
отправителя или без подходящих вложений пропускается.

При первом подключении будут обработаны и помечены прочитанными все непрочитанные письма с вложениями в папке, в том
числе старые. Лучше подключить отдельный ящик или папку.

## Автоопределение типа

Если тип документа неизвестен (`schema=auto` в API, «Определять автоматически» в кабинете, боте и почте), воркер
перед извлечением спрашивает модель клиента по первой странице и списку его типов. Для облака это лёгкая модель
`DOCFLOW_ANTHROPIC_CLASSIFY_MODEL` (по умолчанию `claude-haiku-5-5`); клиент с локальным режимом (Ollama) не отправляет
картинку в облако даже для определения типа. Не определился — документ `failed` с выбором типа и кнопкой «Распознать
заново» (`POST /v1/documents/{id}/retype`).

## Тарифы

Лимит страниц в месяц задаётся тарифом клиента:

| Тариф | Код | Страниц в месяц |
|---|---|---|
| Пробный (новые клиенты) | `trial` | 50 |
| Старт | `start` | 500 |
| Бизнес | `business` | 3000 |
| Без лимита (клиенты, созданные до тарифов) | `unlimited` | — |

Тариф меняет оператор: `docker compose exec api docflow tenant-plan <tenant_id> <код>` (оплаты в продукте нет).
Считаются страницы документов, принятых в календарном месяце по Москве; не считаются `failed`, не дошедшие до извлечения
(определение типа бесплатно).
Лимит проверяется при приёме во всех каналах: API отвечает 402 «Лимит страниц на месяц исчерпан (N из M)», бот отвечает
тем же текстом, письмо пропускается. Документ, начатый в пределах лимита, принимается целиком. Остаток —
`GET /v1/usage` и главная страница кабинета.

## Порты

| Сервис | На хосте | Внутри сети compose |
|---|---|---|
| Сайт | 127.0.0.1:3000 | `web:3000` |
| API | 127.0.0.1:8000 | `api:8000` |
| Postgres | **127.0.0.1:55432** (5432 оставлен локальному Postgres) | `postgres:5432` |
| Redis | 127.0.0.1:6379, с паролем | `redis:6379` |
| S3 (SeaweedFS) | 127.0.0.1:8333 | `s3:8333` |

API, сайт и хранилища опубликованы только на loopback. Секреты (`DOCFLOW_PG_USER`/`DOCFLOW_PG_PASSWORD`,
`DOCFLOW_REDIS_PASSWORD`, `DOCFLOW_S3_ACCESS_KEY`/`DOCFLOW_S3_SECRET_KEY`) compose берёт из окружения или `.env`
(образец — `.env.example`); без них подставляются dev-значения. Файл ключей SeaweedFS генерируется при старте
контейнера из `DOCFLOW_S3_*`.

## Лимиты

`DOCFLOW_MAX_FILE_MB` (20) — один файл, `DOCFLOW_MAX_PAGES` (30) — страниц в документе,
`DOCFLOW_MAX_REQUEST_MB` (200) — всё тело `POST /v1/documents`. Превышение отклоняется (413/422) до постановки
в очередь. В Telegram и из почты лимиты те же; помимо них действует лимит страниц тарифа (см. «Тарифы»).

Точность извлечения меряется на эталонных наборах (формат — `evals/README.md`; настоящие документы в git не
попадают):

```
ANTHROPIC_API_KEY=sk-... uv run docflow eval evals/invoice_ru --extractor claude
```

Отчёт печатается и пишется в `evals/eval-report.json`. Опубликованных замеров на реальных документах пока нет.

## Запуск в проде

API: `uvicorn --factory docflow.api.app:create_app`. Размер тела `POST /v1/documents` ограничен в самом приложении
(`DOCFLOW_MAX_REQUEST_MB`, по умолчанию 200), но лимит нужен и на прокси перед ним — иначе прокси сам буферизует
гигабайты: в nginx `client_max_body_size 200m;` (не больше `DOCFLOW_MAX_REQUEST_MB`).
Задайте `DOCFLOW_PUBLIC_BASE_URL` (внешний адрес API, попадает в `pdf_url` ответов и вебхуков) и
`DOCFLOW_PUBLIC_SITE_URL` (внешний адрес кабинета, например `https://docflow.example.ru`): от него строятся ссылки на
документ и PDF в CRM, Google Таблицах, Excel-реестре, Telegram и письмах. Эти ссылки открываются после входа в
кабинет. Оставите `http://localhost:3000` — ссылки у клиентов не откроются; воркер при старте предупредит об этом в
логе (если не включён `DOCFLOW_WEBHOOK_ALLOW_PRIVATE`). Подробнее — [docs/connectors.md](docs/connectors.md).

Смените все три секрета: `DOCFLOW_PG_PASSWORD`, `DOCFLOW_REDIS_PASSWORD`, `DOCFLOW_S3_ACCESS_KEY` +
`DOCFLOW_S3_SECRET_KEY` (пароль Postgres применяется только при создании тома `pgdata`; на живой базе — `ALTER
USER`). Пароли подставляются в URL без экранирования — используйте буквы, цифры, `-` и `_`.

Никогда не публикуйте наружу порты Redis, Postgres и S3 — в compose они привязаны к `127.0.0.1`, так и оставьте.
Особенно Redis: arq хранит в нём задачи в pickle, и любой, кто может записать в Redis, исполнит свой код в
воркере. API и сайт в `docker-compose.yml` тоже опубликованы только на `127.0.0.1`; в проде ставьте их за прокси с
TLS и публикуйте только прокси.

Каналы приёма: сервис `channels` (`docflow channels`) должен работать всегда, иначе боты молчат, а почта не
забирается. Он использует тот же образ, что и `api`, и те же переменные окружения. `DOCFLOW_SECRETS_KEY` обязателен для
бота и почты: без него подключить их нельзя, а при смене ключа сохранённые токены и пароли придётся ввести заново.
Один бот опрашивается одним процессом: не запускайте две копии `channels` (Telegram ответит конфликтом, и бот встанет на
паузу).
